# 邀请注册系统 —— 技术栈与运作逻辑

> 一个练手用的小网站：注册、登录、邀请码拉新、邀请奖励积分。
> 前端是 React 单页应用，后端是 Spring Boot，前后端通过 JSON API 通信。

---

## 一、技术栈

### 前端（`frontend/`）

| 技术 | 说明 |
| --- | --- |
| React 19 | UI 框架，用函数组件 + Hook |
| Vite 8 | 开发服务器与打包工具（`npm run dev` 跑在 5173 端口） |
| TypeScript 6 | 带类型的前端代码 |
| oxlint | 代码检查（`npm run lint`） |
| 无第三方路由 | 不引 react-router，用 `App.tsx` 里的 `useState` 在 4 个「视图」间切换 |

前端结构：

```
frontend/src/
├── api.ts        后端调用封装 + token 存取（localStorage）
├── format.ts     时间格式化（ISO -> 2026-08-13 14:05）
├── App.tsx       视图状态机：home / register / login / profile
└── pages/        四个页面组件
```

### 后端（`backend/`）

| 技术 | 说明 |
| --- | --- |
| Java 17 | 编程语言 |
| Spring Boot 4 | 应用框架，内置内嵌 Tomcat，跑在 8080 端口 |
| Spring Data JPA + Hibernate | ORM，操作数据库 |
| H2 数据库（文件模式） | 用户数据存在 `backend/data/invite.mv.db` 文件里 |
| spring-security-crypto | 只用它的 BCrypt 做密码哈希（不引入整套 Security 过滤器链） |
| jakarta validation | 请求参数校验（用户名长度、密码长度等） |

后端结构：

```
backend/src/main/java/com/example/invite_system/
├── domain/User.java              用户实体（对应 users 表）
├── repository/UserRepository.java  数据访问层
├── service/
│   ├── UserService.java          注册/登录/个人主页核心逻辑
│   ├── TokenStore.java           token -> 用户 id 的内存映射
│   └── ApiException.java         业务异常（状态码 + 中文提示）
├── web/
│   ├── AuthController.java       注册 / 登录 / 退出 接口
│   ├── MeController.java         个人主页数据接口
│   ├── ApiExceptionHandler.java  统一错误格式 {"message": "中文提示"}
│   ├── BearerToken.java          解析 Authorization: Bearer xxx 头
│   └── dto/                      请求/响应数据结构（record）
└── config/WebConfig.java         CORS 跨域 + BCrypt 编码器 Bean
```

### 数据存储位置（用户信息存哪）

- **用户数据**存在后端目录下的 **H2 文件数据库**：`backend/data/invite.mv.db`
  - 配置见 `application.properties`：`jdbc:h2:file:./data/invite;AUTO_SERVER=TRUE`
  - 后端重启后**用户数据不丢**（落盘在文件里）
  - 想清空数据：删掉 `backend/data/` 目录再启动后端
  - 想直接看表：打开 `http://localhost:8080/h2-console`，JDBC URL 填 `jdbc:h2:file:./data/invite`，用户名 `sa`，密码留空
- **登录态 token**存在**内存**里（`TokenStore` 的 `ConcurrentHashMap`），后端重启后 token 失效，需要重新登录
- **前端**把 token 存在浏览器 **localStorage** 里（key 为 `invite-system.token`），刷新页面后用它自动恢复登录

### 数据表结构（users 表）

| 字段 | 说明 |
| --- | --- |
| id | 自增主键 |
| username | 用户名，唯一 |
| password_hash | BCrypt 哈希，**不存明文** |
| invite_code | 自己的邀请码，注册时随机生成一次，唯一 |
| inviter_id | 邀请人（拉他进来的人）的用户 id，没有则为 null |
| points | 积分，每成功邀请一人 +10 |
| created_at | 注册时间 |

## 二、运作逻辑

### 1. 注册

流程（前端 `RegisterPage.tsx` -> `POST /api/auth/register` -> 后端 `AuthController.register` -> `UserService.register`）：

1. 用户在注册页填写：用户名（2-32 字符）、密码（6-64 字符）、邀请码（**选填**）。
2. 前端把邀请码 `trim` 后，**留空则提交 `null`**。
3. 后端校验：
   - 用户名重名 → 抛 `409`「用户名「xxx」已被注册，请换一个用户名」（先用 `existsByUsername` 查，再靠数据库唯一约束兜底并发情况）
   - 填了邀请码但不是真实存在的码 → 抛 `400`「邀请码无效，请核对后重填，或留空直接注册」
   - 邀请码大小写不敏感，后端会 `toUpperCase()` 后去查
4. 生成新用户：
   - 密码用 `BCryptPasswordEncoder.encode()` 哈希后存储
   - 随机生成 8 位邀请码（字符集 `ABCDEFGHJKLMNPQRSTUVWXYZ23456789`，去掉容易看错的 0/O、1/I/l），生成时保证**不与现有邀请码重复**
   - 记录 `inviterId`（填了邀请码则记为邀请人的 id，否则为 null）
   - 初始积分 0，`createdAt` 为当前时间
5. **发奖**：如果填了有效邀请码，就给邀请人 `addPoints(10)` 并保存（`INVITE_REWARD = 10`）。
6. 注册成功后后端立即签发 token 返回给前端，**不用再跳登录页**，直接进入个人主页。

### 2. 登录

流程（前端 `LoginPage.tsx` -> `POST /api/auth/login` -> `UserService.login`）：

1. 用户填用户名 + 密码提交。
2. 后端按用户名查出用户，用 `passwordEncoder.matches(明文, 库里哈希)` 比对密码。
3. 查不到用户或密码不匹配 → 抛 `401`「用户名或密码错误」（故意不区分是用户名还是密码错，防撞库枚举）。
4. 校验通过后，`TokenStore.issue(userId)` 生成一个随机的 token（`SecureRandom` 24 字节 → Base64 URL 编码），存进内存映射 `token -> userId`，返回给前端。
5. 前端把 token 存入 localStorage。

### 3. 登录态与个人主页

- 前端访问 `GET /api/me` 时带上请求头 `Authorization: Bearer <token>`。
- 后端 `MeController` 用 `BearerToken.from()` 解析出 token，再去 `TokenStore` 查对应用户 id；查不到 → `401`「登录状态已失效，请重新登录」。
- 根据用户 id 查出用户，再查出 `inviterId == 我的 id` 的所有用户（按注册时间从早到晚）作为「我邀请的用户」列表，返回：
  - `username`、`inviteCode`、`points`、`createdAt`、`invitees[]`（用户名 + 注册时间）
- 前端 `App.tsx` 在启动时如果 localStorage 里有 token，就自动调 `/api/me` 尝试恢复登录态；token 失效则清掉 token 退回首页。
- 退出登录：前端调 `POST /api/auth/logout`，后端把内存里的 token 删除，前端同时清掉 localStorage。

### 4. 邀请码拉新（核心链路）

整个拉新机制就是靠 **users 表里的 `invite_code` 和 `inviter_id` 两列**串起来的：

```
A 注册（无邀请码） ──生成自己的邀请码 X──> A.invite_code = X
B 注册（填 X）    ──> B.inviter_id = A.id
                    ──> A.points += 10
C 注册（填 X）    ──> C.inviter_id = A.id
                    ──> A.points += 10
```

- 每个人的邀请码**只在注册时生成一次，之后永不再变**（页面只能复制，不能改）。
- 别人注册时填了你的邀请码，你的 `points` 就 +10。
- 邀请人和被邀请人是一对多关系：一个人可以邀请很多人，一个人只能有一个邀请人（或者没有）。
- 目前是**一层关系**：A 邀请 B 得 10 分，但 B 邀请 C 时，A **不会**再得积分（没有多级返佣）。

### 5. 邀请奖励积分

- 规则：**每成功邀请 1 人，邀请人积分 +10**（代码里的常量 `INVITE_REWARD = 10`）。
- 发奖时机：**被邀请人注册成功的那一刻**，在同一个事务里给邀请人加积分（`@Transactional`），保证「注册成功」和「加积分」要么都发生、要么都不发生。
- 积分的用途目前只是展示数字，没有兑换/消费逻辑。
- 个人主页会显示：我的积分、已邀请人数、我的邀请码（可一键复制）、被邀请用户列表。

## 三、前后端通信方式

- 前端 dev 服务器在 5173，后端在 8080，跨域由后端 `WebConfig` 的 CORS 配置放行（只允许 `localhost:5173` / `127.0.0.1:5173`）。
- 接口一览：

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/auth/register` | 注册，body `{username, password, inviteCode?}`，成功返回 `{token, username}` |
| POST | `/api/auth/login` | 登录，body `{username, password}`，成功返回 `{token, username}` |
| POST | `/api/auth/logout` | 退出，作废当前 token（需带 Authorization 头） |
| GET | `/api/me` | 个人主页数据（需带 Authorization 头） |

- 出错时后端统一返回 `{"message": "中文提示"}`（`ApiExceptionHandler`），前端把 `message` 直接显示给用户。

## 四、如何跑起来

需要两个终端：

```bash
# 终端 1：后端（8080）
cd backend
./mvnw spring-boot:run

# 终端 2：前端（5173）
cd frontend
npm install   # 第一次才需要
npm run dev
```

然后打开 http://localhost:5173 。

## 五、小结（用一句话概括运作逻辑）

> 用户注册时后端生成唯一邀请码并存进 H2 文件库；别人注册时填了你的邀请码，就把它记到你的名下、并在同一事务里给你 +10 积分；登录靠内存 token（前端存 localStorage），用户数据靠 H2 文件持久化，重启后端只丢登录态、不丢用户。
